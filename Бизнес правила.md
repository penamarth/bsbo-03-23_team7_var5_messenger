# Бизнес-правила мессенджера

## Обзор

Система мгновенного обмена сообщениями предназначена для передачи текстовых сообщений, управления чатами, профилями пользователей, уведомлениями и аудио/видео звонками.  
Пользователи взаимодействуют с системой через клиентское приложение, а сервер обеспечивает доставку сообщений, хранение данных, управление профилями и обработку уведомлений.

## Бизнес-правила

| ИД | Правило | Частота и обоснование изменений | Источник |
|---|---|---|---|
| **МСБР1** | Пользователь может отправлять сообщения только в те чаты, участником которых он является | **Очень низкая (раз в 3–5 лет)** – правило доступа является фундаментальным и меняется только при пересмотре модели безопасности | Политика доступа, модель безопасности |
| **МСБР2** | Сообщение считается доставленным, если хотя бы одно устройство получателя подтвердило получение | **Высокая (1 раз в квартал)** – алгоритмы доставки оптимизируются под нагрузку и многоплатформенность | Техническая архитектура, протоколы доставки |
| **МСБР3** | Сообщение можно редактировать только в течение ограниченного времени (например, 48 часов) | **Низкая (раз в 1–2 года)** – изменяется редко, при обновлении UX-политики или требований приватности | Политика конфиденциальности |
| **МСБР4** | Уведомления отправляются только на активные устройства с зарегистрированным deviceToken | **Средняя (1–2 раза в год)** – зависит от изменений API push-шлюзов (APNS/FCM) | Технические требования push-платформ |
| **МСБР5** | Пользователь может изменить никнейм только при прохождении всех проверок (длина, уникальность, допустимые символы) | **Низкая (раз в 1–2 года)** – правила обычно стабильны, но могут корректироваться для предотвращения спама | UX-требования, анти-спам политика |
| **МСБР6** | Удаление чата доступно только его владельцу или администратору (если роль предусмотрена) | **Очень низкая (раз в 3–5 лет)** – базовая логика владения чатом, меняется редко | Политика управления чатами |
| **МСБР7** | Система должна хранить историю сообщений чата до удаления пользователем или автоматически (если есть политика очистки данных) | **Средняя (раз в 1–2 года)** – зависит от требований хранения и законодательства | Политика хранения данных, GDPR-аналог |
| **МСБР8** | Регистрация возможна только после подтверждения телефонного номера через SMS-код | **Низкая (раз в 1–2 года)** – метод идентификации может измениться при переходе на e-mail или OAuth | Регламент аутентификации |
| **МСБР9** | При неуспешной отправке push-уведомления система должна деактивировать токен устройства после нескольких ошибок | **Высокая (каждые 3–6 месяцев)** – правила обновляются из-за изменений API Apple/Google | Технические стандарты APNS/FCM |
| **МСБР10** | В групповой чат можно добавлять нового участника только при согласии владельца группы или по правилам чата | **Средняя (1 раз в год)** – может изменяться при пересмотре модели групп | Модель группового взаимодействия |
| **МСБР11** | Звонок может быть инициирован только если пользователь онлайн или его устройство активно | **Высокая (каждые 1–2 квартала)** – изменения связаны с обработкой статусов присутствия | Логика call-сервиса |
| **МСБР12** | Пользователь может отключить уведомления для конкретного чата (mute), и система не должна отправлять push-уведомления по нему | **Низкая (раз в 1–2 года)** – UX-поведение редко меняется, но политика уведомлений может корректироваться | UX-требования уведомлений |
| **МСБР13** | Сообщения не могут содержать запрещённый контент (если действует модерация) | **Высокая (раз в квартал)** – списки запрещённого контента и алгоритмы модерации обновляются регулярно | Политика безопасности и модерации |
| **МСБР14** | Никнейм пользователя должен быть уникальным в пределах всей системы | **Очень низкая (раз в 5 лет)** – уникальность — базовое требование идентификации | Политика профилей |
| **МСБР15** | В чате должен отображаться последний отправленный или изменённый messageId для формирования списка чатов | **Средняя (1–2 раза в год)** – может меняться при оптимизации списка чатов или добавлении сортировок | UX-требования интерфейса |

# Функциональные возможности (кратко)

### Для пользователей:
- отправка и получение сообщений в реальном времени;
- создание и редактирование чатов;
- изменение профиля (никнейм, аватар);
- управление приватностью;
- получение уведомлений;
- совершение аудио/видео звонков.

### Для системы:
- валидация данных;
- доставка сообщений и уведомлений;
- управление устройствами пользователя;
- хранение истории чатов;
- обработка звонков.

---

# Технические требования (кратко)

- Клиент–серверная архитектура  
- Поддержка push-уведомлений (iOS/Android)  
- REST/WebSocket API  
- Масштабируемые микросервисы: сообщения, профили, чаты, уведомления, звонки  
- Безопасность: шифрование соединений, токены, проверка прав  
- Поддержка устойчивости и логирования
